# [RAG 프로젝트 TIL 2] 점수를 믿기 전에 — RAG 검색·답변 평가하기

> 금융 문서 RAG Agent 프로젝트 정리 2편이에요.
> 1편이 추출과 청킹이었다면, 2편은 **검색과 답변을 어떻게 쟀고, 그 숫자를 믿기 전에 무엇을 확인해야 했는지**예요.

<br>

## 1. 골든셋: 무엇으로 재나

평가하려면 "이 질문의 정답 근거는 이 문서 이 쪽"이 적힌 문항이 필요해요. 4종을 썼어요.

| 골든셋 | 문항 | 내용 |
|:---|:---:|:---|
| table_image (직접 작성) | 189 | 표·그림·수식에 답이 있는 질문 |
| paragraph (직접 작성) | 100 | 본문 문단에 답이 있는 질문 |
| provided (강의 제공) | 180 | 기준 답안, 꼭 들어갈 내용, 피해야 할 오류, 기대 행동 포함 |
| golden_set (표본) | 20 | 프롬프트를 고칠 때 본 문항 |

제공 골든셋에는 기준 답안 말고도 `must_include`(꼭 들어갈 내용), `must_not_include`(피해야 할 오류), `expected_behavior`(되묻기, 범위 밖 안내 등)가 있어서 그대로 채점 기준으로 썼어요.

<br>

## 2. 검색 평가: hit@k와 MRR

LLM 없이 검색만 재는 지표예요.

- **hit@k:** 정답 근거가 상위 k개 안에 있는 문항 비율
- **MRR:** 정답이 처음 나온 순위의 역수 평균 (1위면 1, 2위면 0.5, 5위면 0.2)

### 검색 방식 비교

| 방식 | 설명 |
|:---|:---|
| Similarity | 벡터 유사도 |
| MMR | 비슷한 것끼리 겹치지 않게 다양하게 |
| BM25 | 키워드 검색 (한국어는 Kiwi로 형태소 분석) |
| **Hybrid** | 벡터 + BM25를 5:5로 섞기 (`EnsembleRetriever`) |

모든 근거 유형(본문·표·그림·수식)에서 **Hybrid가 1위**였어요. 벡터만, BM25만 쓸 때보다 섞을 때 확실히 좋았고, 가중치는 0.5~0.7 사이에서 차이가 없어서 5:5로 뒀어요.

### 리랭커는 효과가 있었지만 쓰지 않았다

`bge-reranker-v2-m3`로 다시 정렬하니 hit@1이 0.633 → 0.767로 올랐어요. 그런데 노트북 CPU에서 **질문당 15초**가 걸렸어요. hit@5가 이미 0.94~0.97이라 정답 근거는 대부분 5개 안에 있어서, 리랭커 대신 **상위 5개를 모두 답변 LLM에 넘기고** 고르는 건 LLM에게 맡겼어요.

> 효과를 재기 전에 속도부터 표본으로 재 보자. 처음부터 437문항을 돌려서 20분을 날렸다.

<br>

## 3. 답변 평가: RAGAS 대신 채점 LLM 한 번

RAGAS는 지표마다 LLM을 여러 번 부르고 토큰을 따로 모으기 어려웠어요. 골든셋에 채점 기준이 이미 있어서, **채점 LLM을 한 번** 불러 이렇게 채점했어요.

| 지표 | 뜻 |
|:---|:---|
| correctness | 기준 답안과 비교한 점수 (1 / 0.5 / 0), 이것의 평균이 "정답률" |
| faithfulness | 답을 주장 단위로 쪼갰을 때 근거에 있는 주장의 비율 (지어내기 확인) |
| must_include / must_not | 꼭 들어갈 내용이 있나, 피해야 할 오류가 없나 |
| behavior_ok | 기대 행동(되묻기, 범위 밖 안내)을 했나 |

그리고 틀린 이유를 나눴어요.
- **검색 실패:** LLM에 넘긴 근거에 정답 쪽이 아예 없음
- **답변 실패:** 근거는 있었는데 틀림

<br>

## 4. 숫자를 믿기 전에 확인해야 했던 것들

이번 프로젝트에서 가장 많이 배운 부분이에요.

### (1) 자동 분류를 믿지 말고 오답을 직접 열어 보기

첫 답변 평가에서 실패 3문항 중 2개가 "답변 실패"로 분류됐어요. 그런데 열어 보니 **실제로는 검색 문제**였어요.

- 현금흐름표 질문: 설명 청크만 오고, 숫자가 든 **표 조각은 안 옴**
- 계산 질문: 2쪽은 왔는데 계산 방식이 있는 **3쪽이 안 옴**

쪽 단위 hit@5는 정답 쪽의 아무 청크나 오면 맞은 걸로 쳐서, 필요한 조각이 빠져도 몰랐어요. 그래서 **검색된 청크의 앞뒤 청크(걸친 표는 전체 조각)를 같이 넘기게** 했고, 정답률이 0.775 → 0.825로 올랐어요.

자동 분류만 믿었으면 검색 문제를 프롬프트로 고치려 했을 거예요.

### (2) 고친 문항과 확인하는 문항을 나누기

프롬프트에 "결론 → 근거 → 주의점" 구조를 넣었더니 고칠 때 본 20문항에서 0.825 → **0.950**이 됐어요. 그런데 처음 보는 30문항에서는 0.850 → **0.883**이었어요.

| | 고칠 때 본 20문항 | 처음 보는 30문항 |
|:---|:---:|:---:|
| 개선 폭 | +0.125 | +0.033 |

차이만큼이 "시험 문제를 보고 고친" 효과예요. 그 뒤로는 모든 비교를 **고칠 때 보지 않은 문항**으로 다시 확인했고, 표본을 새로 뽑을 때도 앞 표본과 겹치지 않게 했어요.

### (3) 같은 설정도 다시 돌리면 흔들린다

같은 설정을 다시 돌려도 1~2문항은 0.5 ↔ 1.0으로 바뀌었어요. LLM 답변도, 채점도 흔들려요. 그래서
- 30문항에서 1~2문항 차이는 **잡음**으로 보고
- 중요한 비교는 **두 번 돌려 평균**을 내고
- **원인을 설명할 수 있는 변화**만 근거로 삼았어요.

### (4) 오답만 골라 다시 잴 때는 안 고친 것도 다시 재기

남은 오답 26문항만 골라 프롬프트 규칙을 더했더니 0.500 → 0.731이 됐어요. 효과가 큰 것 같았는데, **아무것도 안 고치고 다시 돌리기만 해도 0.635**였어요. 오답 중 일부는 원래 운이 나빠서 틀린 거라 다시 돌리면 맞거든요.

> 오답만 골라 다시 재면 점수는 저절로 오른다. 비교 기준은 "안 고친 것을 다시 돌린 점수"여야 한다.

### (5) 채점 기준이 너그러우면 문제가 안 보인다

용어집 문항은 "용어집 파일 안에만 있으면 정답"으로 채점하고 있었어요. 정의가 있는 쪽으로 엄격하게 다시 채점하니 hit@1이 **0.394**로, 절반 넘게 틀리고 있었어요. 너그러운 채점이 청킹 문제를 가리고 있었던 거예요.

### (6) 측정 방식 자체가 틀릴 수도 있다

Agent의 faithfulness가 0.667로 나와서 지어내기를 걱정했는데, 열어 보니 범위 밖 질문에 "국세청에서 확인하세요"라고 안내한 문장이 "근거에 없는 주장"으로 잡힌 거였어요. 근거 없이 답한 경우를 근거 대비로 잰 **측정 함정**이었어요.

<br>

## 5. 프롬프트 개선과 규칙의 부작용

점수가 깎인 문항을 모아 보니 패턴이 셋이었어요.

1. 핵심은 맞혔는데 **"주의할 점"을 빼먹음**
2. **"문서에서 찾을 수 없다"를 너무 빨리 말함**
3. 모델이 **문서 기준일을 모름**

그래서 규칙 묶음 A(결론 → 근거 → 주의점), B(문서 기준일), C(있는 만큼은 답하기)를 더했어요. 그런데 규칙마다 부작용이 있었어요.

| 규칙 | 부작용 | 고친 방법 |
|:---|:---|:---|
| B: 문서 기준일 2026-09-03 | **모든 답에** 날짜를 붙여서 "근거에 없는 숫자"로 감점 | "미래 연도, 최신 정보를 물을 때만" |
| C: 투자 권유 거절 시 분산 설명 | **상관없는 약관 질문에도** 분산투자 문장이 붙음 | "투자 권유를 요청할 때만" |

> 규칙 하나가 다른 답에 새어 나간다. 특정 질문용 규칙은 **언제 쓰는지**까지 적어야 하고, 고칠 문항과 함께 **나빠지면 안 되는 문항**도 같이 돌려야 한다.

<br>

## 6. 기록: 결과를 어디에 남기나

- 문항별 결과는 JSONL, 실행마다 요약 한 줄은 `runs.jsonl`에 이어 붙였어요. SQLite도 고민했지만 바이너리라 팀 레포에서 git diff로 리뷰가 안 돼서 JSONL로 했어요.
- `run_id`로 설정·문항별 결과·요약을 연결하고, 청킹을 바꾼 뒤에는 청크 파일 지문(`chunks_md5`)도 남겨서 어떤 청크로 돌린 결과인지 구분했어요.
- LLM을 부를 때마다 토큰과 비용을 비용 기록 md에 자동으로 한 줄씩 추가했어요. 전체 프로젝트 비용은 약 $34였어요.
- 180문항을 돌리다 Gemini 서버 혼잡(503)으로 멈춰서 **$1.5를 날렸어요.** 그 뒤로 붐비면 30초 → 1분 → 2분 → 4분 기다렸다 다시 시도하고, 문항마다 중간 저장해서 이어서 할 수 있게 했어요.

<br>

## 정리

1. **오답은 직접 열어 보기.** "답변 실패"가 사실은 검색 문제였다.
2. **고친 문항과 확인하는 문항을 나누기.** 고칠 때 본 문항의 점수는 부풀려져 있다.
3. **흔들림을 감안하기.** 두 번 돌려 평균, 원인을 설명할 수 있는 변화만 믿기.
4. **오답만 다시 잴 때는 안 고친 것도 다시 재기.**
5. **채점 기준과 측정 방식도 의심하기.**
6. **오래 걸리는 실행은 중간 저장부터.**

다음 편에서는 LangGraph로 Agent를 만들고, 기본 RAG와 **공정하게** 비교한 과정을 정리할게요.
