# [RAG 프로젝트 TIL 3] LangGraph로 RAG Agent 만들고 기본 RAG와 공정하게 비교하기

> 금융 문서 RAG Agent 프로젝트 정리 3편(마지막)이에요.
> 1편은 추출·청킹, 2편은 평가였고, 3편은 **LangGraph Agent 설계, 비용 줄이기, 기본 RAG와의 공정한 비교**예요.

<br>

## 1. 기본 RAG와 Agent는 무엇이 다른가

- **기본 RAG:** 질문 → 검색 1번 → 답변 1번. 끝.
- **Agent:** 질문을 먼저 분류하고, 근거가 부족하면 검색어를 바꿔 다시 찾고, 상황에 맞게 답해요.

공정하게 비교하려고 두 방식은 **검색 도구, 답변 프롬프트, 채점이 모두 같고 그래프 구조만** 달라요. 그래서 검색 코드를 평가 스크립트에서 떼어 `SearchTool` 하나로 모았고, 옮기기 전과 후의 검색 결과를 57문항에서 비교해 **모두 같은 것**을 확인했어요.

<br>

## 2. Agent 구조

```
질문
 → classify  (document / clarify / out_of_scope)
 → retrieve  (Hybrid 상위 5개 + 이웃 청크)
     ├─ document        → grade (이 근거로 답할 수 있나?)
     │                     ├─ 충분 → generate
     │                     ├─ 부족, 재검색 2회 미만 → rewrite (검색어 바꾸기) → retrieve
     │                     └─ 부족, 재검색 다 씀 → generate
     └─ clarify / out_of_scope → generate
 → generate (결론 → 근거 → 주의점)
```

| 분류 | 이런 질문 | Agent가 하는 일 |
|:---|:---|:---|
| `document` | "주택연금은 무상 지원금인가요?" | 검색 → 근거 판단 → 부족하면 다시 찾기 (최대 2회) |
| `clarify` | "수수료가 얼마야?", "**이** 펀드 수익률은?" | 상품마다 어떻게 다른지 근거로 설명하고 되묻기 |
| `out_of_scope` | "2027년 세액공제 한도는?" | 문서 기준일에는 없다고 밝히고 관련 규정 + 최신 자료 안내 |

LangGraph 코드는 이렇게 생겼어요.

```python
def after_retrieve(state):
    # 되묻기·범위 밖 질문은 근거를 더 찾아도 답이 정해지지 않아서 재검색하지 않는다
    return "grade" if state["route"] == "document" else "generate"

def after_grade(state):
    if state["enough"] or state["retries"] >= MAX_RETRIES or not state["next_query"]:
        return "generate"
    return "rewrite"

graph = StateGraph(AgentState)
for name, fn in (("classify", classify), ("retrieve", retrieve), ("grade", grade),
                 ("rewrite", rewrite), ("generate", generate)):
    graph.add_node(name, fn)
graph.add_edge(START, "classify")
graph.add_edge("classify", "retrieve")
graph.add_conditional_edges("retrieve", after_retrieve, ["grade", "generate"])
graph.add_conditional_edges("grade", after_grade, ["generate", "rewrite"])
graph.add_edge("rewrite", "retrieve")
graph.add_edge("generate", END)
app = graph.compile()
```

- **종료 조건:** generate가 끝나면 끝. 재검색은 최대 2회라서 검색은 최대 3번, LLM 호출은 최대 5번이에요.
- **상태(State)에 사용량도 누적:** LLM 호출 수, 검색 수, 입력·출력 토큰, 모델별 사용량. 비교 실험할 때 바로 꺼내 쓸 수 있어요.

## 3. 설계하면서 바뀐 결정들

### 되묻기에도 근거가 필요하다

처음 설계에는 "정보가 부족하면 검색 없이 바로 되묻기" 노드가 있었어요. 그런데 기준 답안을 다시 보니 이랬어요.

> "청약 철회는 상품마다 7일, 14일 등으로 다르니 어떤 상품인지 알려 주세요."

되묻는 것도 **근거를 들어 설명하면서** 되묻는 거였어요. 그래서 검색 없는 되묻기 노드를 없애고, 검색한 뒤 답변 노드에서 되묻게 바꿨어요.

### v1에서 v2로: 분류 실수와 헛된 재검색

v1을 돌려 보니 문제가 둘 있었어요.

| 문제 | 고친 방법 |
|:---|:---|
| "**이** 펀드 수익률은?"을 범위 밖으로 분류 → 어떤 펀드인지 묻지 않음 | 대상이 특정되지 않으면 최신 수치를 묻더라도 `clarify` |
| 투자 권유 질문에서 "투자자 성향 정보가 없다"며 재검색 2번을 다 씀 (문서에 원래 없는 정보) | 재검색은 `document`만, 투자 성향·판정 요구는 빠진 정보로 보지 않기 |
| 범위 밖 안내가 문서에 있는 관련 내용(약관 별첨 등)을 놓침 | **범위 밖도 검색**하고 답변에서 안내. 검색 없이 끝나는 노드가 없어져서 그래프가 오히려 단순해짐 |

v2 확인은 **v1을 고칠 때 본 표본과 겹치지 않는 새 30문항**으로 했어요.

<br>

## 4. 비용 줄이기: 어디에 돈이 쓰이는지부터

### 실패: 쉬운 노드를 싼 모델로 (E9-a)

"분류·근거 판단은 쉬우니까 가벼운 모델(Flash-Lite)로 바꾸자"고 해 봤어요.

| | 정답률 | 비용 |
|:---|:---:|:---:|
| 전부 3.6 Flash | 0.900 | $0.41 |
| 분류·판단만 Lite | 0.900 | $0.36 (−12%) |

- 비용은 12%만 줄었어요. 비용의 대부분(78%)은 **답변 작성**이었거든요.
- 대신 Lite 분류기는 `clarify`를 **한 번도 고르지 않았어요.** 되묻기 기능을 잃었어요.
- 분류는 원래 생각을 최소로(`minimal`) 해서 30문항에 $0.01 정도였어요. **아낄 게 없는 곳을 바꿔서 기능만 잃은 거예요.**

### 성공: 답변의 "생각"을 줄이기 (E10)

돈이 쓰이는 곳은 답변 작성이고, 그 출력의 대부분은 **생각(thinking) 토큰**이었어요. 모델은 그대로 두고 `reasoning_effort="low"`로 낮춰 봤어요.

| 생각 수준 | 출력 토큰 | 시간 | 계산 맞음 |
|:---|---:|---:|:---:|
| 기본 | 3,341 | 15.8초 | O |
| `low` | **614** | **4.5초** | O |

30문항으로 확인해도 정답률은 그대로, **비용 −36%, 시간 −38%**였어요.

> 모델을 바꾸기 전에 같은 모델의 설정부터 보자. 그리고 비용은 쓰이는 곳부터 줄이자.

재미있었던 점은, 짧은 분류에서는 `low`가 거의 효과가 없었는데(517 → 459 토큰) 생각할 거리가 많은 답변에서는 82%가 줄었다는 거예요. 같은 설정도 일에 따라 효과가 달라요.

<br>

## 5. 공정한 비교: 한쪽만 다이어트시키지 않기

E10 직후에는 "Agent가 기본 RAG보다 싸고 빠르다"는 결과가 나왔어요. 그런데 **Agent만** 생각을 줄인 상태였어요. 한쪽만 다이어트시켜 놓고 체중을 비교한 셈이에요.

그래서 다시 맞췄어요.
- 두 방식 모두 답변 생각 `low`
- 채점 LLM은 답변 LLM과 **분리**해서 고정 (처음엔 같은 객체를 써서, 답변 설정을 바꾸면 채점도 같이 바뀔 뻔했어요)
- 30문항은 흔들림과 구분이 안 돼서 **120문항, 4개 셋**으로 늘림

| 120문항 (같은 조건) | 기본 RAG | Agent |
|:---|:---:|:---:|
| 정답률 | 0.854 | **0.904** |
| LLM 호출 / 검색 (문항당) | 1 / 1 | 3.15 / 1.23 |
| 시간 / 비용 (문항당) | **5.3초 / $0.005** | 8.8초 / $0.009 |

- **4개 셋 모두 Agent가 높았어요** (+0.033 ~ +0.067). 나은 문항 14, 못한 문항 5라서 이번엔 잡음이 아니라 효과라고 말할 수 있었어요.
- **비용은 뒤집혔어요.** 같은 조건이면 기본 RAG가 1.7배 쌌어요. Agent 비용은 분류·근거 판단·재검색 때마다 근거를 다시 넣는 **입력 토큰** 때문이에요.

Agent가 확실히 나았던 곳은 평균보다 **유형**에서 보였어요.
- **되묻기:** "청약 철회할 수 있어?" → 상품마다 7일·14일로 다르다고 설명하고 상품을 되물음 (0.5 → 1.0, 네 번 돌려 모두 같음)
- **재검색:** 첫 검색에 없던 다른 쪽 근거를 찾아냄

**결론:** Agent는 비용·시간 1.7배로 정답률 +0.05. 문항당 1센트 미만·9초라 상담 서비스라면 쓸 만해요. 문서 질문만 있는 곳이라면 기본 RAG가 효율적이에요.

## 6. 마지막 다듬기: 규칙끼리 부딪힌다

청킹 개선 뒤 제공 골든셋 전체를 돌리니 Agent 정답률이 0.928이었어요. 남은 오답을 줄이려고 몇 가지를 더 해 봤어요.

| 시도 | 결과 |
|:---|:---|
| 근거 판단을 질문의 부분마다 하게 | 한 문항만 좋아지고 재검색어가 엉뚱해짐 → **되돌림** |
| 분산투자 설명은 투자 권유 요청 때만 | 상관없는 질문의 분산 문장 사라짐 → **채택** |
| "되묻기 질문에서 가정하지 말라" 강화 | 그대로 가정함 → **되돌림** |

되묻기가 안 고쳐진 이유가 흥미로웠어요. "이 계좌는 배우자가 이어받을 수 있어?"에 Agent가 "네, 연금저축이라면 가능"이라고 가정해서 답했는데, 원인은 **규칙 충돌**이었어요. 답변 구조 규칙의 "1. 결론: 질문에 바로 답하세요"가 결론 칸을 채우게 만든 거예요. 규칙을 더하는 게 아니라 이 유형의 답변 구조 자체를 바꿔야 했어요.

마지막으로 기준 답안이 문서 밖의 상식·계산을 요구하는 2문항을 평가에서 빼고(이유를 파일로 남김), **178문항 Agent 0.933, 기본 RAG 0.899**로 마무리했어요.

<br>

## 정리

1. **Agent는 공정하게 비교하자.** 검색 도구·프롬프트·채점을 같게 두고 그래프만 다르게.
2. **설계는 기준 답안을 보고.** 되묻기에도 근거가 필요했다.
3. **비용은 쓰이는 곳부터, 모델보다 설정부터.** 쉬운 노드를 싼 모델로 바꾸면 기능만 잃는다.
4. **한쪽만 좋게 만들었으면 다른 쪽도 맞춰서 다시 재기.**
5. **Agent의 효과는 평균보다 유형별로 보인다.** 되묻기·범위 밖·흩어진 근거.
6. **규칙을 더할수록 다른 규칙과 부딪힌다.**

## 시리즈를 마치며

3일 동안 가장 크게 남은 건 "**원인을 고치면 점수가 따라온다**"였어요. 프롬프트를 다듬은 효과(+0.033)보다, 오답을 직접 열어 보고 청킹 문제를 고친 효과(+0.03~0.05)가 더 컸어요. 그리고 그 원인은 대부분 자동 지표가 아니라 **오답을 하나씩 열어 볼 때** 보였어요.
