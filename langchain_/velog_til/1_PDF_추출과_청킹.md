# [RAG 프로젝트 TIL 1] PDF의 표는 그림이다 — 금융 PDF 추출과 청킹

> 금융 문서 PDF 23개(490쪽)로 RAG Agent를 만들면서 배운 것들을 3편으로 정리해요.
> 1편은 **PDF에서 글자·표·그림을 뽑고 청크로 나누는 단계**, 2편은 평가, 3편은 LangGraph Agent예요.

## 프로젝트 한 줄 요약

- **무엇:** 금융 문서(용어집, 표준약관 15개, 가이드북, 보고서 6개)를 검색해서 근거(파일명·페이지)와 함께 답하는 RAG Agent
- **스택:** Python, pdfplumber, LangChain, LangGraph, Gemini, Chroma
- **최종 결과:** 검색 hit@5 0.954, 답변 정답률 0.933 (제공 골든셋 178문항)

그런데 이 숫자의 상당 부분은 모델이나 프롬프트가 아니라 **추출과 청킹**에서 나왔어요.

## 1. pdfplumber가 보는 표는 눈에 보이는 표와 다르다

처음엔 `page.extract_text()`와 `find_tables()`면 될 줄 알았어요. 그런데 표가 계속 깨졌어요. 원인을 하나씩 찾아보니 전부 **"PDF의 표는 선과 점과 상자로 그린 그림"**이라는 데서 나온 문제였어요.

| 증상 | 실제 원인 | 해결 |
|:---|:---|:---|
| 첫 열·마지막 열 값이 빠짐 | 표에 **바깥 세로 테두리가 없음** | 표 양 끝에 세로선을 직접 지정해서 다시 찾기 |
| 점선 행이 안 나뉨 | 점선이 선이 아니라 **길이 0짜리 점 수백 개** (pdfplumber는 3pt보다 짧은 선을 버림) | 같은 높이에 늘어선 점들을 가로선 하나로 이어 붙이기 |
| 화살표 있는 표가 두 개로 쪼개짐 | 화살표 줄에는 세로선이 없음 | 테두리가 온전한 헤더 행의 x좌표를 아래 조각에 이어받기 |
| 같은 문장이 수십 번 반복 | 페이지 **배경 상자**가 표로 잡히고, 병합 셀 채우기로 복사됨 | 셀 하나가 1000자를 넘으면 표가 아니라 배경으로 보기 |
| 왼쪽·오른쪽 문장이 한 줄씩 섞임 | **두 쪽을 한 장에 펼친** 페이지 | 가로로 긴 쪽은 왼쪽 반 / 오른쪽 반 따로 추출 |

점선 문제를 예로 들면, 고치기 전과 후가 이렇게 달라요.

```diff
- | 복권기금 정부 일반회계 출연금 소계 금융회사출연금 기타 | 1,750 - 1,750 95 - | ...
+ | 정부 출연금 | 복권기금 | 1,750 | 1,750 | ...
+ | 정부 출연금 | 일반회계 | - | - | ...
+ | 정부 출연금 | 소계 | 1,750 | 1,750 | ...
```

### 고치면 반드시 전체를 다시 비교

가장 많이 배운 건 이거예요. **한 쪽을 고친 규칙이 다른 쪽을 망가뜨린 적이 매번 있었어요.**

- 헤더 열 경계를 이어받게 했더니 → 막대그래프가 "칸이 다 빈 표"로 잡힘
- 세로 점선도 쓰게 했더니 → 빨간 강조 상자의 옆변이 가짜 열을 만듦

그래서 이전 결과를 저장해 두고, 바뀐 표를 전부 비교해서 "행이 줄거나 빈칸이 늘어난 표가 없는지" 확인하는 걸 습관으로 만들었어요. 원문 쪽 캡처와 추출 결과를 나란히 놓은 비교용 md도 문서마다 만들어 두었어요.

## 2. 표가 깊이를 가질 때: 계층 경로

보고서 표에는 이런 들여쓰기 계층이 많아요.

```
가계신용(A+B)
  가계대출(A)
    주택담보대출
    기타대출
  판매신용(B)
```

행을 나누는 것만으로는 "가계대출이 가계신용의 일부"라는 관계가 사라져요. 원문은 그 관계를 **들여쓰기와 점선 괄호**로만 보여주니까요. 그래서 첫 열에 상위 항목 경로를 붙였어요.

```
| 가계신용(A+B)                               | 1,861.3 | ...
| 가계신용(A+B) > 가계대출(A)                  | 1,755.5 | ...
| 가계신용(A+B) > 가계대출(A) > 주택담보대출     | 985.4   | ...
| 가계신용(A+B) > 판매신용(B)                  | 105.8   | ...
```

나중에 청킹에서 표가 300자 단위로 쪼개졌을 때, `판매신용` 행만 있는 조각도 이 경로 덕분에 상위 항목을 알 수 있었어요.

## 3. 깨진 표·그림은 Gemini로, 숫자는 원문과 대조

수식이 깨진 표, 테두리가 없어 인식이 안 되는 표, 그림으로 들어간 그래프는 규칙으로 고치기 어려웠어요. 방법을 비교해 봤어요.

| 방법 | 판단 | 이유 |
|:---|:---:|:---|
| OCR | X | 디지털 PDF라 글자는 이미 정확함. 문제는 글자가 아니라 **표 구조** |
| marker | △ | 설치가 무겁고, 표 품질은 결국 LLM 보정에 기댐 |
| **Gemini + 숫자 검증** | 채택 | 점선·병합·수식에 강함. 숫자는 원문과 대조해서 막음 |

비전 LLM은 표를 눈으로 보듯 잘 읽지만, **숫자를 지어낼 수 있어요.** 금융 문서에서는 치명적이에요. 그래서 이렇게 했어요.

```
깨진 표·그림 영역만 캡처 → Gemini → 숫자 검증 → 통과한 것만 사용
```

- **숫자 검증:** Gemini가 낸 숫자가 그 영역의 원문 텍스트(또는 OCR 결과)에 없으면 지어낸 숫자로 보고 버려요.
- **결과 고정:** Gemini는 같은 입력에도 매번 조금씩 다르게 답해서, 한 번 통과한 결과는 다시 부르지 않아요.

실제로 검증이 잡아낸 사례가 있었어요. 한 그래프에서 Gemini가 축의 연도를 열 이름으로 쓰고 `22.6`처럼 **없는 값을 만들었는데**, OCR 대조에서 걸러졌어요.

## 4. 청킹: 조각만 봐도 무엇인지 알 수 있게

청크 크기는 300자/겹침 50과 500자/60을 비교해서 **300/50**으로 정했어요 (검색 hit@5 0.938 vs 0.920). 크기보다 중요했던 건 **조각 하나만 떼어 봐도 무엇인지 알 수 있게** 만드는 일이었어요.

### 표 조각마다 제목 반복

큰 표는 행 단위로 나누는데, 나눈 조각에 헤더(`| 항목 | 금액 |`)만 있고 제목이 없으면 LLM이 그 숫자가 무엇인지 몰라요. 그래서 조각마다 표 제목·단위·헤더를 반복해서 붙였어요. 답변 정답률이 0.725 → 0.775로 올랐어요.

### 오답에서 출발한 청킹 개선 3가지

180문항을 전부 돌리고 나서 오답을 청킹 관점으로 다시 봤더니, 고칠 게 더 있었어요.

**(1) 용어집: 용어 하나 = 청크 하나**
- 300자마다 자르니 청크 하나에 **용어 4~5개**가 섞였어요.
- 게다가 뒤쪽 출처 목록(용어 이름 / URL)이 용어집 청크의 **44%**였어요. 용어 이름이 정확히 같아서 키워드 검색에서 1등을 하지만, 정의는 없어요.
- PDF를 보니 용어는 글자 크기 11, 설명은 10이었어요. **글자 크기로 정확히 나눴어요.**
- 정의가 있는 쪽 기준 hit@1 **0.394 → 0.727**

**(2) 약관: 청크마다 "[약관 이름] 제○조(제목)" 머리말**
- 약관 청크의 91%가 조항 중간부터 시작해서 "무슨 약관 몇 조"인지 알 수 없었어요.
- 머리말을 붙이니 약관 문항 hit@5가 0.864 → 0.909로 올랐어요.
- 그런데 **다른 질문이 1위에서 7위로 떨어졌어요.** "외국집합투자증권" 약관의 모든 청크에 약관 이름이 붙으면서, 키워드 검색(BM25)에서 "집합", "투자"가 수백 번 반복된 거예요.
- 그래서 머리말은 **벡터 검색과 LLM에 넘기는 글에만** 쓰고, 키워드 색인에서는 뺐어요.

> 같은 정보도 검색 방식에 따라 약이 되기도, 잡음이 되기도 한다.

**(3) 잡음 정리: 약관 출처 목록, 보고서 2단 편집**
- 약관에도 용어집과 같은 출처 목록이 있었어요 (약관 청크의 23%). 한 문서에서 찾은 문제는 다른 문서에도 있는지 확인해야 해요.
- 2단 편집 보고서는 왼쪽·오른쪽 문장이 한 줄로 섞여서 단마다 따로 추출했어요.
  - 처음 정한 2단 판정 기준은 절반 이상이 **표 칸 사이 빈 공간**을 2단으로 오해했어요. 숫자만 보지 말고 실제 쪽 이미지를 열어 봐야 했어요.

| 437문항 | 개선 전 | 용어집 | + 약관 머리말 | + 잡음 정리 |
|:---|:---:|:---:|:---:|:---:|
| hit@1 | 0.703 | 0.716 | 0.725 | **0.748** |
| hit@5 | 0.938 | 0.945 | 0.952 | **0.954** |

이 청킹 개선만으로 180문항 답변 정답률이 기본 RAG **0.844 → 0.894**, Agent **0.897 → 0.928**로 올랐어요. 프롬프트를 고친 것보다 효과가 컸어요.

## 5. 삽질 모음: Windows 한글 경로와 Chroma

**증상:** 임베딩은 끝났는데 검색하면 `Error loading hnsw index`

- 처음엔 "쓰는 도중에 다른 프로세스가 읽어서 깨졌다"고 추측했는데, 다시 만들어도 똑같았어요.
- 색인 폴더를 열어 보니 HNSW 본체 파일(`data_level0.bin`)이 아예 없었어요.
- **한글 경로에서는 `.bin` 파일이 안 생기고, 영문 경로에서는 정상**이었어요. 처음 테스트는 벡터 200개라 색인 파일을 쓰는 단계(1,000개)까지 가지 않아서 놓쳤어요.

**또 하나:** 같은 질문인데 실행 순서에 따라 검색 결과가 바뀌었어요. Chroma는 HNSW 색인을 1,000개(`sync_threshold`)마다만 디스크에 쓰는데, 1,916개짜리 컬렉션은 절반 가까이가 디스크에 안 쓰인 상태였어요. `hnsw:sync_threshold`를 청크 수에 맞춰 다시 만들었더니 해결됐어요.

> 평가 숫자가 실행 순서에 따라 바뀌면, 모델보다 저장소부터 의심하자. 그리고 테스트는 실제 규모로 하자.

## 정리

1. **PDF의 표는 그림이다.** 선, 점, 곡선, 배경 상자가 섞여 있어서 눈에 보이는 표와 pdfplumber가 보는 표가 다르다.
2. **고치면 반드시 전체 비교.** 한 쪽을 고친 규칙이 다른 쪽을 망가뜨린다.
3. **LLM에 맡긴 숫자는 원문과 대조.** 비전 LLM은 잘 읽지만 지어내기도 한다.
4. **청크는 혼자 떼어 봐도 무엇인지 알 수 있게.** 표 제목, 계층 경로, 약관 머리말.
5. **고친 건 최종 답변까지 따라가 보기.** 추출에서 고친 계층이 청킹·검색을 거쳐 답변에 쓰이는지까지 봐야 해결이다.

다음 편에서는 이 검색과 답변을 **어떻게 평가했는지**, 그리고 점수를 믿기 전에 확인해야 했던 것들을 정리할게요.
