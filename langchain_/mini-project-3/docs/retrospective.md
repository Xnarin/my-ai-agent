# 회고

## 설계와 구현 과정에서 배운 점

- State와 저장 데이터는 다르다. 처음에는 State 표에 잔액, 계좌 ID, 거래 시각처럼 JSON 파일에 저장되는 항목까지 적었다. 작업하면서 State는 단계 사이에 넘겨야 할 값을 적는 칠판이고, 은행 데이터는 JSON 파일에 있는 장부라는 차이를 알게 됐다. 이후에는 “다음 단계나 분기에서 이 값을 써야 하나?”를 기준으로 State에 넣을지 판단했다.
- 검사는 노드에서 하고, 결과는 State에 남긴다. 처리할 수 없는 이유를 State에 적어 두면 분기는 그 값만 보고 다음 경로를 정할 수 있다. 결과를 안내할 때도 같은 값을 쓸 수 있었다. 직접 구현해 보니 책임, State 변경, 분기가 노드를 나누는 기준이라는 말이 이해됐다.
- 검사와 실행을 나누는 게 중요하다. 승인 전에 먼저 검사하고, 승인 후에만 데이터를 변경했다. 계좌와 카드 데이터를 바꾸는 곳도 한 곳으로 모아서, 거절되거나 실패한 요청은 데이터에 영향을 주지 않도록 했다.

## 어려웠던 점과 해결 과정

- 처음에는 설계 초안을 어떻게 써야 할지 막막했다. 다른 업무의 흐름도를 참고해 요청 예시, 처리 순서, 상자와 분기, State 표, 분기 표 순으로 작성하면서 형식을 익혔다.
- 업무마다 흐름도를 따로 그려야 하는지도 헷갈렸다. 업무를 조회형과 변경형으로 나눠 보니 대부분 비슷한 흐름이었다. 그래서 흐름도 한 장에 업무별 가지를 추가했다. 카드 분실 정지를 넣을 때도 새 단계를 만들지 않고 이체와 같은 “검사 → 승인 → 실행” 단계를 사용했다.
- 처음에는 불가 조건으로 잔액 부족과 상대 계좌 오류밖에 떠올리지 못했다. AI 검토를 받은 뒤 과제 문서의 별명 중복, “-1만 원” 예시를 다시 살폈다. 그 과정에서 출금 계좌 확인, 같은 계좌로의 이체, 0 이하 금액, 정보 누락 조건을 보완했다. 계좌를 찾아야 잔액을 확인할 수 있으므로 검사 순서도 정했다.
- 이체 범위가 모호했다. 처음에는 상대 계좌 ID로 보내는 경우까지 생각했다. 하지만 과제 예시가 모두 본인 계좌 간 이체였기 때문에, 본인 계좌끼리 별명으로 이체하는 것으로 범위를 정했다.

## 남은 한계와 개선하고 싶은 점

- 되물은 요청도 처리 기록에는 “실패”로 남는다. 정보가 부족해 질문한 경우를 따로 구분하면 기록을 더 정확하게 남길 수 있다.
- 승인은 “승인”과 “거절”만 받는다. “응, 진행해”나 “아니, 5만 원만” 같은 자연어 응답과 승인 전 수정은 아직 처리하지 못한다.
- 계좌와 카드는 이름이 정확히 같아야 찾을 수 있다. 띄어쓰기가 다르면 찾지 못하고 후보만 안내한다.
- 구현한 업무가 아직 적다. 거래 내역 조회, 청구서 납부, 카드 일시 잠금·재발급은 구현하지 못했다. 현재 구조에서는 검사·실행 함수를 만들고 업무 종류를 추가하면 된다.
