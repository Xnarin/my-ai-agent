# 회고

## 설계와 구현 과정에서 배운 점

- **State와 저장 데이터는 다르다.** 처음 State 표에 잔액, 계좌 ID, 거래 시각 같은 JSON 칸을 적었다. State는 단계끼리 넘겨야 하는 값만 적는 칠판이고, 은행 데이터는 JSON 파일(장부)에 있다는 걸 구분하게 됐다. "다음 단계나 분기가 이 값을 봐야 하나?"로 판단하면 된다.
- **검사는 노드에서 하고 결과는 State에 남긴다.** 불가 이유를 State에 적어 두니, 분기는 그 값만 보고 방향을 정하고 결과 안내도 안 되는 이유를 말할 수 있었다. 노드를 나누는 기준(책임, State 변경, 분기)이 무슨 뜻인지 직접 느꼈다.
- **interrupt로 멈춘 노드는 재개할 때 처음부터 다시 실행된다.** 그래서 승인 요청 노드에서는 데이터를 바꾸지 않고, 실제 변경은 다음 노드(변경 실행)에서만 했다.
- **Checkpointer는 이전 요청의 State를 그대로 가지고 있다.** 요청마다 불가 이유, 결정, 결과를 초기화하지 않으면 이전 요청의 결과가 새 요청의 안내에 섞인다.
- **검사와 실행을 나누면 안전하다.** 승인 전에 검사하고 승인 후에만 실행하며, 계좌와 카드 데이터를 바꾸는 곳이 한 곳뿐이라 거절하거나 실패하면 데이터가 그대로 남는다.
- **LLM은 해석만 맡기고, 검사·변경·안내는 코드로 만들었다.** 결과를 예측하고 assert로 확인하기 쉬웠다. 처리 결과 확인처럼 대화 맥락으로 대상을 찾아야 하는 곳에만 LLM 답변을 썼다.

## 어려웠던 점과 해결 과정

- **설계 초안을 어떻게 써야 할지 몰랐다.** 다른 업무의 예시 흐름도를 참고해서 요청 예시 → 처리 순서 문장 → 상자와 분기 → State 표 → 분기 표 순서로 써 보며 형식을 익혔다.
- **업무마다 흐름도를 따로 그려야 하는지 헷갈렸다.** 업무를 흐름 모양(조회형, 변경형)으로 나눠 보니 대부분 모양이 같았다. 그래서 흐름도 한 장에 업무를 가지로 추가하기로 했다. 실제로 카드 분실 정지를 추가할 때 단계를 새로 만들지 않고, 이체와 같은 "검사 → 승인 → 실행" 단계를 함께 썼다.
- **불가 조건을 두 개(잔액 부족, 상대 계좌 오류)밖에 떠올리지 못했다.** AI 검토를 받으면서 과제 문서의 문구(별명 중복, "-1만 원" 예시)를 다시 보고 출금 계좌 확인, 같은 계좌, 금액 0 이하, 정보 누락을 보완했다. 계좌를 찾아야 잔액을 볼 수 있어서 검사 순서도 정했다.
- **이체 범위가 모호했다.** 처음에는 상대 계좌 ID로 보내는 경우를 생각했지만, 과제 예시가 모두 본인 계좌 간 이체라서 본인 계좌끼리 별명으로 이체하는 것으로 범위를 좁혔다.
- **정보가 빠진 요청을 흐름도를 바꾸지 않고 처리하고 싶었다.** 빠진 정보를 불가 이유 자리에 질문으로 넣고, 다음 입력을 같은 대화의 앞 요청과 합쳐 해석하게 해서 해결했다.

## 남은 한계와 개선하고 싶은 점

- **재시작하면 대화와 승인 대기가 사라진다.** MemorySaver는 메모리에만 저장한다. 파일에 저장하는 Checkpointer로 바꾸고, 재시작 후에는 진행 중이던 업무를 안내한 뒤 다시 승인받게 하고 싶다.
- **변경 저장과 처리 기록 저장이 따로 일어난다.** 둘 사이에 프로그램이 꺼지면 변경은 반영되고 기록만 빠질 수 있다. 변경 함수 안에서 함께 저장하도록 바꾸고 싶다.
- **되물은 요청도 처리 기록에 "실패"로 남는다.** 정보가 빠진 경우를 따로 구분하면 기록이 더 깔끔해진다.
- **승인은 "승인"과 "거절"만 받는다.** "응, 진행해", "아니, 5만 원만" 같은 자연어 승인과 승인 전 수정은 아직 안 된다.
- **이름이 정확히 같아야 계좌와 카드를 찾는다.** 띄어쓰기가 다르면 찾지 못하고 후보를 안내한다.
- **구현한 업무가 적다.** 거래 내역 조회, 청구서 납부, 카드 일시 잠금·재발급은 하지 못했다. 지금 구조에서는 검사·실행 함수를 만들고 업무 종류만 추가하면 된다.
- **처리 결과 확인 답변은 LLM이 만든다.** 처리 기록을 근거로 하지만 표현이 매번 조금씩 달라서, 이 부분은 눈으로 확인했다.
